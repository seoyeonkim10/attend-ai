## A. 제품 방향과 시장 검증

**핵심 현장 문제**: 종이 출석부/수동 체크로 인한 학생 검색 시간, 기록 누락/오체크, 교사의 반복 확인, 지각·결석 사유 제출/검토의 분절.

**우선 가설**: 바코드 체크인과 학생별 기록, 사유 신청/승인/정정 및 감사 기록을 하나의 역할 기반 흐름으로 제공하면 담당 교사의 출결 업무를 줄일 수 있다. 실제 가치는 파일럿 중 수동 확인에 소요된 시간, 오류 수정 횟수, 사유 처리 시간을 *사전에 정의한 기준*으로 측정한다.

**경쟁사 차별화 가설(미검증)**: 학교 맞춤형 규정, 학생에게 보이는 투명한 신청 상태, 학급별 최소 권한, 승인 근거/감사 이력, 학생증 미소지 대체 절차. 별도 경쟁사 비교표와 학교 담당자 인터뷰 필요.

**도입 장애물**: 개인정보 처리 근거와 학교 승인, 담당 교사의 변경 관리, 미성년자 정보·증빙 안전성, 학내 학생증 데이터 정의, 연결 장애 대비 수기 절차, 장기 운영 책임자 부재, 실제 총비용, 기존 출결 시스템 연동 여부.

### 알려진 불일치/기술 부채

1. 승인 결과는 `attendance_requests`에만 반영. **출결 확정/수정은 별도 작업**이며 UI에 명시.
2. 학생 학급 드롭다운에서 본인 `class_members` SELECT 정책 부족으로 조회 실패했던 사례가 있음. 재발 방지용 권한 테스트 필요.
3. `attendance_requests` 접근 GRANT가 초기 SQL 파일에 빠져 실제 학생 INSERT 시 권한 오류 발생. 이후 수동 GRANT로 해결됨. 운영용 마이그레이션에서 권한/정책을 분리해 명시해야 함.
4. 기존 `README.md`는 정적 데모 초기 설명으로 현재 Auth 기능을 반영하지 않음.
5. 프리뷰는 공개 GitHub Pages를 사용. 민감정보를 취급하는 운영용 SaaS 배포에 적절한 호스팅인지 별도 결정 필요.

## D. 개발 로드맵

### P0 — 학교 시범 운영 전에 필수
- RLS와 Postgres GRANT, `SECURITY DEFINER` 함수 전수 검토.
- 교사/학생/학교 관리자 분리, 담당 반 외 접근 차단 통합 테스트.
- 출결 원본 변경과 사유 승인 내역에 대한 불변 감사 기록.
- 교사·학생의 신청 상태 정합성 및 최종 출결 변경 절차.
- 바코드 인증 흐름을 서버 측에서 검증(단순 클라이언트 바코드 문자열로 임의 출석 처리 금지).
- 오류·중복 출석·수기 출석 대체 및 관리 책임/학교 규정.
- 가상 데이터만 사용한 신뢰성·보안 시험, 학교 승인.

### P1 — 출시 전 권장
- 비공개 증빙서류 보관/삭제, 학교 규정 설정의 관리자 승인 워크플로.
- 상세 통계, 성능/모바일/접근성/모니터링, 관리자가 계정을 일괄 발급·회수할 수 있는 흐름.
- 사용자 안내문, 개인정보처리방침, 백업·복구 시나리오.

### P2 — 초기 학교 테스트 이후
- AI 규정 보조 및 누락 정보 탐지(인간 최종 결정), 기존 학사 시스템 연동, 고급 통계 및 자동화, 여러 학교용 멀티테넌시 청구/운영 기능.

## E. 0원 개발 범위와 비용 한계

- GitHub + GitHub Actions: 개발 버전 관리와 **가상 데이터 데모**에 사용.
- Supabase Free: Auth·Postgres·RLS·작은 테스트 데이터 가능. 공식 요금표상 Free 프로젝트 DB 약 500MB, 파일 저장 약 1GB(요금과 정책은 수시 변경 가능).
- 무료 개발로 가능한 것: 권한 테스트, 가상 학생·교사 샘플, 학생 신청/교사 승인 UI, 수기 출결, 개발 전용 바코드 시험, 비공개 버킷 구성 실험.
- 불확실한 비용: 실제 운영 도메인, 인증 이메일/SMS 발송, 학교 규모 저장공간, 백업·로그 장기 보존, 보안 검토, 장애 대응·지원. 무료 용량은 **학교 서비스 가능성의 보장**이 아님.
- GitHub Pages 공식 제한에 따르면 상업용 SaaS 호스팅 수단으로 사용해서는 안 되며 민감한 거래에도 권장되지 않음. 운영 서비스는 학교의 보안·법무 담당자 승인과 적합한 배포 대안 검토가 필요함.

## G. 최초 개발 작업과 안전 경계

1. 개발 브랜치의 학생/교사 화면에서 신청 승인과 공식 출결 수정의 차이를 명시하고, 신청 목록 조회 오류를 숨기지 않도록 개선.
2. 위 테스트 조건을 GitHub에 버전 관리.
3. 다음 기술 작업: **RLS/GRANT 검증용 읽기 전용 진단 SQL**, 이후 감사 로그 스키마 제안 및 검토. SQL 적용 전 영향 범위/백업 방법 안내 및 승인 필요.
4. 운영 DB 정책, 기존 출결, 사용자 권한을 자동으로 변경하지 않음. `main` 브랜치 병합/운영 배포는 별도 승인 필요.

## H. 테스트 절차 (가상 데이터)

1. 학생 A 로그인 → 출결 2건 확인 → 신청 제출 → 접수 상태 확인.
2. 학생 B 로그인 → 학생 A의 기록/신청이 조회되지 않는지 확인.
3. 교사 A 로그인 → 본인 담당 학생 신청 확인 → 승인/반려 → 학생 A 결과 확인.
4. 교사 B 로그인 → 담당하지 않는 반의 신청/출결 접근 불가 확인.
5. 승인 후 기존 출결 기록이 자동으로 바뀌지 않는지 확인하고, 교사가 별도로 정정 후 이력이 남는지 검증.
6. 승인 처리 실패·중복 신청·네트워크 끊김·미배정 학생·브라우저 재접속 테스트.
